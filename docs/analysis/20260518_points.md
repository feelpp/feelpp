# Point Sets and Point Integrals

## Context

`markedpoints(mesh, marker)` currently represents points declared as `Physical Point()` in Gmsh. In practice these are mesh vertices, so their integration support can be obtained directly from the marked mesh entity and no geometric search is required.

Point loads and point moments also need a second use case: integrating over arbitrary physical coordinates that are not necessarily vertices. Those points need localization in the mesh before assembly, and for the intended point-source semantics we only need one owning element per point.

## Semantics

- `markedpoints(mesh, marker)` remains the vertex-based API. It is tied to mesh point entities and should keep the fast path for already localized vertices.
- A new point-set concept should represent arbitrary coordinates. A tentative name is `physicalpoints`, but the key requirement is that these points are not assumed to be mesh vertices.
- Arbitrary point sets should be localized with the existing kd-tree/localization machinery.
- If a point lies on an inter-element boundary, the integration contract should select one admissible element. The point-source load must not be duplicated over all adjacent elements.
- If a point cannot be localized, assembly should throw with the marker/name and coordinates.

## Phased Plan

### Phase 1: Make the Existing Semantics Explicit

- Document that `markedpoints()` is a mesh-entity range over physical vertices.
- Keep the current efficient assembly path for marked vertices.
- Add or keep tests that exercise point forces and point moments on marked vertices.

### Phase 2: Introduce an Arbitrary Point Container

- Add a lightweight container for named point sets loaded from config/JSON.
- Store each point as coordinates plus optional metadata such as marker/name and component/direction payload.
- Keep this layer independent of a specific variational form so it can be reused by point forces, point moments, probes, and reference checks.

### Phase 3: Localize Arbitrary Points

- Use the existing kd-tree/localization tool to map each coordinate to one mesh element.
- Cache the localized result as `(point, element id, reference coordinates)` so repeated assembly/checks do not redo localization.
- Throw on localization failure, dimension mismatch, or invalid point data.

### Phase 4: Extend Point Integration

- Extend `integrate(...)` or add an overload that accepts localized arbitrary point sets.
- Preserve the current `markedpoints()` path as the fast vertex-specialized path.
- For arbitrary points, evaluate the integrand on the selected element at the localized reference coordinates and accumulate one contribution per input point.

### Phase 5: Validation

- First test: define arbitrary points that coincide with actual mesh vertices and compare the assembled result with `markedpoints()` for the same coordinates.
- Add force and moment cases using both APIs, with identical final displacement checks up to a tight tolerance.
- Add a non-vertex interior-point test once the localization-backed integration path is stable.

## Open Questions

- Naming: `physicalpoints` is natural but could be confused with Gmsh `Physical Point()`, which is vertex-based. A name such as `points(mesh, marker)` or `localizedpoints` may make the distinction clearer.
- Boundary policy: selecting one element is appropriate for point loads/moments, but it should be documented because it differs from integrating over all adjacent support entities.
