== Ambiguities & Resolutions

=== Member variable naming
*Ambiguity:* Documentation references both `M_member` and `_member` conventions (⚠️ verify).

*Resolution:* Require `M_PascalCase` for new code while allowing existing `PascalCase_` members through the tidy ignore regex.

*Impact:* `.clang-tidy` enforces the preference without flagging the legacy suffix style.

=== Exception types
*Ambiguity:* Guidance alternates between `std::runtime_error` and custom exception wrappers.

*Resolution:* Default to `std::runtime_error` or project-specific subclasses that communicate context; avoid raw integers or `std::exception` bare throws.

*Impact:* Documented for reviewers; no automated check yet.

=== Include guards vs `#pragma once`
*Ambiguity:* Older docs prefer include guards while newer files mix approaches.

*Resolution:* Accept `#pragma once` for new headers. When touching legacy guarded headers, keep the guard.

*Impact:* Communicated via docs only.

=== `constexpr` and `noexcept`
*Ambiguity:* Docs recommend them without explicit tooling enforcement.

*Resolution:* Encourage usage when semantics allow. Leave final judgement to reviewers while modernize checks highlight obvious cases.

*Impact:* No direct tooling change beyond existing `modernize-*` coverage.

=== MPI and Kokkos synchronization
*Ambiguity:* HPC guidance warns about implicit barriers but lacks actionable wording.

*Resolution:* Document best practices: avoid global barriers inside hot loops, capture only required data in `KOKKOS_LAMBDA`, and state synchronisation choices explicitly.

*Impact:* Awareness via AGENTS and CONTRIBUTING; no automated guard yet.
